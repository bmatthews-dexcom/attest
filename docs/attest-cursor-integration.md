# attest → Cursor integration — recommendation

## 1. TL;DR

Treat Cursor as a **second build target**, not a drop zone. Mirror the existing `scripts/build-target-claude.mjs` with a new `scripts/build-target-cursor.mjs` that generates a `.cursor/` tree (skills, custom subagents, rules, `hooks.json`, `mcp.json`) from the same canonical sources in `/workspace`, and ship a small `attest-mcp` server that exposes the 79 shell validators + the phase-gate state machine as native MCP tools so Cursor's agent can call them directly. Drop the OpenCode-specific compact-agent / tier-detection / resume-anchor machinery — frontier Cursor models with 200 k–1 M context do not have the compaction and small-model failure modes those systems exist to patch. "Just copy the markdown" is wrong because it leaves the validators disconnected (nothing fires them), the delegation router without a host, the HANDOFF paste protocol semantically meaningless in a single-agent UX, and the SDLC phase gates reduced to prose that nothing enforces.

## 2. What attest actually is

The marketing line is "expert agent system." The concrete thing is a build-and-install pipeline whose output is a cross-cutting *governance layer* for an agent IDE — personas, protocols, deterministic scripts, and gates — originally wired for OpenCode but structured as source-of-truth with a second generated target (`attest-claude`).

**How the pieces talk.** The spine is the SDLC Lead (`agents/sdlc-lead.md`) with its four `/sdlc <mode>` entry points (init / onboard / feature / improve) plus a `/guide` concierge (`agents/guide.md`). Everything downstream is reached via a **HANDOFF document** (`agents/shared/HANDOFF_TEMPLATES.md`, `agents/shared/BOUNDED_TASK_CONTRACT.md`), which is a strict text contract: `ROLE / CONTEXT / WRITE-SCOPE / PRODUCE / VERIFY / Completion Manifest / completion phrase`. The *mechanism* that runs the HANDOFF is picked by `agents/shared/EXECUTOR_SELECTION.md` from a 4-way matrix driven by two capability flags written to `docs/work/.model-context`:

- **A** — native Task tool (dispatch HANDOFF as subagent prompt).
- **B** — subprocess (`tools/task.ts` → `opencode run --agent --dir <workcopy>`).
- **C** — write to `docs/work/HANDOFF_<agent>.md`, print pointer, human opens specialist as first-class conversation.
- **D** — inline (coordinator reads the specialist's file and runs its methodology in the same turn).

Autonomy is `interactive` by default (C for every skilled specialist) or `auto` (unattended — A→B→D, C forbidden). Every HANDOFF return triggers the 6-step gate-scoring protocol (`agents/shared/GATE_SCORING_PROTOCOL.md`); every phase advance runs `scripts/validators/run-coverage-loop.sh <phase>`, which wraps `validate-phase-gate.sh` and caps the fix-and-reverify loop at 3 iterations. The `scripts/conductor/conductor.mjs` is a special auto-mode case: it claims tickets from `docs/work/plan.json`, spawns an opencode session per ticket in an isolated git worktree, runs validators from outside the session, reviews on a different model, and merges — a complete unattended Phase 4.

**Key cross-cutting protocols** (all under `agents/shared/`): `MODEL_ADAPTER.md`, `CONTEXT_BUDGET.md`, `LOCAL_LLM_PRIMER.md`, `MICRO_LOOP.md`, `LOOP_PREVENTION.md`, `CHECKPOINT_STATE.md`, `TUI_SESSION_HYGIENE.md`, `PERSISTENCE.md`, `AUTONOMY_PROTOCOL.md`, `CHALLENGER_PROTOCOL.md`, `GAUNTLET_LOOP.md`, `RALPH_WIGGUM_LOOP.md`, `FIX_VERIFY_LOOP.md`, `MEMORY_PRIMER.md`. These are read-on-demand references (`description: 'Reference document — read on demand, not an agent.'`, `disable: true`) and `scripts/build-agents.mjs` keeps the five mandatory boilerplate blocks in sync across every agent file.

**Install footprint.** `install.sh` copies `agents/ skills/ commands/ references/ exemplars/ tools/ hooks/ plugins/ scripts/ .semgrep/` into `~/.config/opencode/` (or `.opencode/` with `--project`), writes `experts-version`, overlays `dist/compact-agents/*.md` on top of `agents/` when `--compact` is set, and merges `opencode.json` with Context7 and playwright-search MCP entries. The `attest-claude` sibling is built by `scripts/build-target-claude.mjs` — a `--check` (CI gate) / `--write` script that walks `COPY_GLOBS` + `COPY_FILES` + `OVERRIDES`, applies ordered `PROSE` then `PATHS` transforms (opencode→claude renaming), diffs against the generated repo, and reports skill parity. That script is the exact template for a Cursor build target.

## 5. Why "just copy agents and skills into `.cursor/`" is wrong

Each bullet is a concrete failure mode a naive copy produces today, not a hypothetical:

1. **The 79 validators do not fire.** They are shell scripts whose trigger points are hard-coded into the OpenCode orchestrator agent's prose ("after this HANDOFF returns, run `scripts/validators/run-coverage-loop.sh phase-3`"). Dropping the scripts into `.cursor/scripts/` places them on disk; nothing calls them. The orchestrator prose that references them is instructions to a model that will not have any reason to run them unless explicitly told, and nothing closes the gate when it does not run them. Fix: wire them via `.cursor/hooks.json` (`afterFileEdit` for fast per-file, `stop` for phase gate) AND expose via `attest-mcp` as native tools.

2. **The delegation router (`EXECUTOR_SELECTION.md`) has no host for 2 of its 4 executors.** Executor B (`opencode run --agent --dir <workcopy>` subprocess) does not exist in Cursor — there is no `cursor run --agent` CLI with the same semantics. Executor C (`autonomy=interactive`: write HANDOFF to disk, print pointer, human opens the specialist as a first-class conversation) is a semantic mismatch — Cursor's UX is one agent with Task-launched subagents, not a user juggling parallel sessions and pasting between them. On a naive copy, every agent whose prose says "write HANDOFF to `docs/work/HANDOFF_<x>.md` and tell the user which `/skill` to open" produces advice the user cannot act on in Cursor's single-agent chat.

3. **Tier detection has nothing to detect.** `scripts/detect-model-context.sh` probes LM Studio for a loaded model and context window; writes `docs/work/.model-context` with `tier=small|medium|large`. Cursor models are all large (200 k+). The compact-agent overlay (`dist/compact-agents/`) is 32 agent files replacing the primaries with shorter variants for 32k models — pointless to install, actively harmful (strips reasoning the agent benefits from on frontier models). On a naive copy, the SDLC Lead's `Step 2b — Restore cross-session memory` block cites a `tokenBudget: <600 small / 1500 medium / 3000 large, per docs/work/.model-context>` the agent has no way to resolve.

4. **The resume anchor hook (`plugins/resume-anchor.ts`) is OpenCode-specific experimental API.** It uses `experimental.chat.system.transform` to re-inject disk state into every request — Cursor has no equivalent (its closest, `beforeSubmitPrompt`, can only decide `continue: true|false`, not inject). On a naive copy, the plugin never loads; the discipline the SDLC Lead relies on ("the runtime re-injects this ledger's status into every turn, so trusting it costs nothing") silently stops holding, and the orchestrator keeps making decisions on the assumption it does.

5. **Expert-hooks (`plugins/expert-hooks.ts`) silently does not load.** It is a `@opencode-ai/plugin` default export; Cursor does not read `plugins/*.ts`. On a naive copy, dangerous `rm -rf /`, `git push --force`, `DROP TABLE` go through unblocked; writes to `.env`, `*.key`, SSH private keys go through; post-edit prettier/eslint/tsc/secret-scan does not run; telemetry does not log; the session-model receipt (the "opus ran silently and nobody knew" guard) does not fire.

6. **Build-target divergence drifts immediately.** The entire reason `scripts/build-target-claude.mjs` exists is that "apply every change to both repos" as a manual rule fails — the Claude v1.23.0 release famously shipped untouched because the author forgot the second commit. A Cursor port that is a one-time file copy accumulates the same divergence over the next three releases. Fix: ship Cursor as a build target with a `--check` CI gate on parity.

7. **The HANDOFF intake block becomes dead ceremony.** Every subagent in attest starts with a 60-line "HANDOFF intake (MANDATORY)" block whose rule 1 is "if a `docs/work/HANDOFF_*.md` path appears anywhere in your prompt, read that file before you reply." Cursor's Task tool passes the subagent prompt inline — there is no `docs/work/HANDOFF_<x>.md` file to read because the primary never wrote one. The intake block executes, finds no file, degrades to the fallback — but the rest of the agent's prose assumes the intake block pulled in context the fallback never produced.

8. **Autonomy=auto vs autonomy=interactive gates fire or do not fire from the wrong signals.** `agents/shared/AUTONOMY_PROTOCOL.md` reads `autonomy` from `docs/work/.model-context` and gates every discovery interview, every Gate A/B human approval, every destructive git operation on it. The script that writes `.model-context` requires LM Studio or an OpenAI/Anthropic/Google API key to be set — in Cursor, none of those are set and the file never exists. Every autonomy check falls through to `interactive`, which is correct for a user-at-keyboard flow but means attempts to use attest with a Cursor cloud agent or Automation always pause on gates. This is actually the right default; the problem is the system doesn't **know** it's auto, so logging to `docs/work/APPROVALS.md` never happens.

9. **`task.ts` (the subprocess dispatcher) is unrunnable.** It spawns `opencode run --agent <x>` — Cursor does not have that binary. Any agent whose prose or any skill whose `scripts/` references `tools/task.ts` fails as soon as it is invoked, and the system is designed around that tool being the auto-mode dispatcher.

10. **The conductor is wholly unrunnable.** `scripts/conductor/conductor.mjs` wraps `opencode run --agent` as its session-per-ticket executor, writes to `docs/work/CONDUCTOR_HALT.md`, locks on `.git/conductor.lock`, assumes the `opencode-local` sync wrapper for local models. None of that applies in Cursor. The entire "unattended Phase 4" story is dark on a naive copy.

11. **References to `~/.config/opencode/` resolve to a path that does not exist in Cursor installs.** Every agent file I read had `read(filePath="~/.config/opencode/agents/shared/HANDOFF_TEMPLATES.md")` or similar. On a naive Cursor copy, those reads fail; the fallback path listed in some files is `.opencode/`, also absent. The transform table in `build-target-claude.mjs` is exactly what you need to prevent this — but without the build target, every one of those references goes stale.

## 6. Recommended integration — primary shape and phased rollout

**Primary shape (E, honestly): a multi-layer build target + MCP + hooks hybrid**, split across the three Cursor surfaces each piece naturally fits:

- **Build target (`scripts/build-target-cursor.mjs` in attest, output goes to a Cursor directory tree — either in a sibling `attest-cursor` repo or `.cursor/` of a consuming repo).** Generates `.cursor/skills/`, `.cursor/agents/`, `.cursor/rules/`, `.cursor/hooks.json`, `.cursor/mcp.json`, `.cursor/references/`, and `.cursor/scripts/` from the same canonical sources. Reuses `scripts/build-target-claude.mjs` structure (`COPY_GLOBS`, `COPY_FILES`, `OVERRIDES`, PROSE+PATHS transforms, `--check` CI gate, skill parity check). This is the only piece that solves drift long-term.

- **`attest-mcp` MCP server (new package).** Wraps the 79 validators and the phase-gate state machine as native MCP tools. Also exposes:
  - **Tools (shipped names)**: `validate_<name>` (one per validator shell script), `phase_gate_check(currentPhase, nextPhase)` (gate state machine; collapses the earlier `.gate.current` / `.gate.run` / `.gate.history` sketches), `route_goal(goal)` (the `/guide` router as a tool), `list_experts({ cluster?, phase? })` (primary-expert catalog with `ported` flag). The HANDOFF-template surface ships as MCP **prompts** (`prompt_expert_<id>`, `prompt_sdlc_mode_<mode>`) rather than a tool, so the agent materialises a well-formed body via a prompt call instead of a free-form "handoff.next" tool. Conductor tools (`run_autopilot_task`, …) ship from `attest-conductor` (a separate BDK agent), not from `attest-mcp`.
  - **Resources**: `attest://docs/sdlc/SDLC_TRACKER.md`, `attest://docs/work/STATE.md`, `attest://docs/work/.model-context` (even if attest has nothing to put there on Cursor, the resource lets the agent discover its own context budget), the phase-receipt JSONs under `docs/work/gates/`.
  - **Prompts**: the HANDOFF templates (`agents/shared/HANDOFF_TEMPLATES.md`) as parameterized MCP prompts the agent can call to materialize a well-formed HANDOFF body.
  - Ships as a stdio server configured once per project in the generated `.cursor/mcp.json`. Portable across Cursor + OpenCode + Claude Code (all three support MCP), which is also a nice side effect for maintenance.

- **Hooks layer (`.cursor/hooks.json` + `.cursor/hooks/*.sh`).** The subset of plugin behavior that genuinely wants to fire on every tool call:
  - `beforeShellExecution` → `block-dangerous.sh` (verbatim port of `expert-hooks.ts` DANGEROUS_BASH list — `rm -rf /`, `DROP TABLE`, `git push --force`, `git reset --hard`, any npm registry push, `curl | bash`, `wget | bash`)
  - `preToolUse` with `matcher: "Write|Edit"` → `block-credentials.sh` (verbatim port of BLOCKED_FILE_PATTERNS — `.env`, `credentials.json`, `*.key`, `id_rsa`)
  - `afterFileEdit` → `post-edit-check.sh` wrapping prettier/eslint/tsc/ruff/black/gofmt per file extension, plus the SECRET_PATTERNS regex scan — the single hook replaces `expert-hooks.ts`'s `tool.execute.after`
  - `postToolUse` → `telemetry.sh` appending to `docs/work/telemetry.jsonl` (counts only, same disable env `EXPERTS_TELEMETRY=0`)
  - `sessionStart` (**local only** — cloud agents cannot run it) → `inject-state.sh` emits `{ "additional_context": "$(cat docs/work/STATE.md)" }` — the small, cheap replacement for resume-anchor
  - `stop` → `end-of-turn-gate.sh` runs the current-phase validator and reports gaps; agent decides whether to continue (via `followup_message`)

- **Rules + skills + custom subagents for the personas.** Every attest primary agent becomes both a `.cursor/skills/<name>/SKILL.md` (so the user can `/<name>`) and a `.cursor/agents/<name>.md` (so other agents can `Task(agent="<name>", ...)`). The skill body prompts the agent to call `route_goal({ goal })` first, then dispatch via Task to the right subagent. Shared protocols (`agents/shared/*.md`) become `.cursor/rules/*.mdc` with `description` + `@file` pointer — read on demand, not inlined. `agents/shared/includes/`, `agents/shared/blocks/` content stays in `.cursor/references/`.

- **BDK project (`attest-conductor/bot/`) for the unattended / cloud / Automation surface.** The conductor and `/autopilot` outer loop reimplemented as a BDK agent: `defineAgent` for the top-level, `defineConnection` to the project's git + GitHub, child subagents per cluster, `defineEval` for the planted-defect fixtures. GitHub channel wakes it up on PR events. Memory lives in `ctx.host.kv` (ticket board, delegation log). Deployable to Cursor-managed hosting with `bdk deploy` or self-hosted.

- **Drops.** `plugins/resume-anchor.ts`, `dist/compact-agents/` and the `--compact` install path, `scripts/detect-model-context.sh` and the tier split, `tools/task.ts` (replaced by Cursor's Task tool), `tools/write.ts`/`append.ts`/`update.ts` (fixes for an LM-Studio-plus-OpenCode write bug that does not exist in Cursor), all `~/.config/opencode/` path references.

### Phased rollout

Phasing is sized by invasiveness, not calendar — each phase is a merge-worthy slice.

**Phase 0 — Prove the build target shape (smallest viable slice).**
Scope: `scripts/build-target-cursor.mjs` emits a `.cursor/` tree for ONE skill (`/guide`), ONE custom subagent (`guide`), the full `attest-mcp` tool `route_goal({ goal })` wrapping the routing table, and `.cursor/hooks.json` with `block-dangerous.sh` + `block-credentials.sh`. Add `npm run build:cursor:check` to CI mirroring `build:claude:check`. Dogfood by installing into a Cursor repo and verifying `/guide` routes a goal and the dangerous-bash blocker fires. Success criterion: a Cursor user can `/guide` and get routed to a specific `/skill-name` suggestion that exists in `.cursor/skills/`.

**Phase 1 — Bulk expert port + validators via MCP.**
Scope: every primary agent → skill + subagent pair via the build target; every shared protocol → rule with `@file` pointer; `attest-mcp` extended with all 79 validators and the phase-gate state machine; `.cursor/hooks.json` wired for `afterFileEdit` + `stop`. All OpenCode-isms (`~/.config/opencode/`, `.opencode/`, `opencode.json`, `opencode run`) rewritten in the transforms table (reuse `build-target-claude.mjs` PROSE+PATHS as the starting point, extended with Cursor equivalents). Skill-parity check (same mechanism as the Claude target) ensures no primary agent is silently missing. Dispatch prose across every orchestrator agent rewritten from the 4-executor matrix (A/B/C/D) to the 2-executor Cursor matrix (Task tool + inline), with `/in-cloud` called out as the explicit isolated-work escalation. Success criterion: a Cursor user can run `/sdlc init` end-to-end on a greenfield project, every validator fires at its gate, and the phase gate opens or holds on the same conditions as OpenCode.

**Phase 2 — Conductor as BDK agent.**
Scope: `attest-conductor` BDK project reimplements `scripts/conductor/conductor.mjs` as a `defineAgent` with GitHub channel + `ctx.host.kv` memory. The isolated-worktree-per-ticket loop uses `/in-cloud` cloud subagents instead of `opencode run` subprocesses. `defineEval` cases cover the four `evals/fixtures/` planted-defect scenarios. Success criterion: a BDK-deployed `attest-conductor` claims a 2-ticket PR board, dispatches cloud subagents per ticket, re-reviews on a different model, and merges — the same end-to-end the autopilot `v3.9.0` release proved on OpenCode.

**Phase 3 — Polish, drop obsolete, document.**
Scope: delete the OpenCode-only `tools/*.ts` from the Cursor target output; delete the compact-agent overlay; delete tier-detection references; add `docs/CURSOR_INSTALL.md`; land eval parity between the two targets. Dual-release discipline: tag `attest` and `attest-cursor` together, mirror the hygiene baked into the Claude target.

## 7. Alternatives considered

**B — MCP server only (ship `attest-mcp`, nothing else).**
*Shape:* no skills, no agents, no rules in the Cursor repo. One `.cursor/mcp.json` entry; everything attest offers reachable through `route_goal`, the per-validator `validate_<name>` tools, `phase_gate_check`, and the HANDOFF-template MCP prompts (`prompt_expert_<id>`, `prompt_sdlc_mode_<mode>`).
*Why ranked lower:* loses the entire persona surface. The user cannot type `/security --fix` and get the security-auditor's workflow — they get a tool call that returns a text blob they then paste back. attest's whole value model is "many specialists each with their own prompt + methodology"; collapsing that into tool calls on a single generic agent loses the context-isolation and persona depth that makes the system work. MCP-only is a good *baseline* and we take it as a *component*, but not the whole integration.

**C — BDK project only (reimplement attest as one or several Cursor Background Development Kit agents).**
*Shape:* `attest-cursor/bot/` with `defineAgent` for sdlc-lead, child agents for each cluster, validators and router as tools, SDLC state in `ctx.host.kv`, Slack/GitHub channels, scheduled autopilot.
*Why ranked lower:* BDK is agent-as-code for *bots that go talk to things on their own* (Slack, PRs, cron, webhooks). It's the wrong home for an interactive IDE companion. attest's primary user story is "I'm in my editor, I say `/sdlc feature`, specialists do work in my repo" — the editor-side surface is skills + subagents + rules, not a hosted bot the user talks to over HTTP. BDK IS the right home for the conductor and `/autopilot` outer loops — hence Phase 2 of the recommendation uses it there — but shipping the whole system this way means the editor experience is reduced to "message the hosted bot," which is a regression vs OpenCode.

**D — Hooks + Rules hybrid (no MCP server).**
*Shape:* personas via rules (`.cursor/rules/*.mdc`), validators via hooks (`.cursor/hooks.json` + scripts), no `attest-mcp`.
*Why ranked lower:* rules are static context (`description` + body + optional glob), they are not interactive. Encoding 33 primary agents + 32 cluster specialists as rules bloats the always-on context catastrophically or hides them behind globs that will not match the user's prose intent ("harden this before launch"). Hooks can enforce gates but cannot answer "which specialist should run?" — the router has nowhere to live. Skills + subagents are the right surface for personas; hooks + rules alone cannot carry the surface area.

**A — Build target only (no MCP, no new hooks beyond the plugin port).**
*Shape:* just `scripts/build-target-cursor.mjs` generating `.cursor/*` directly from source.
*Why ranked lower:* leaves the validators and the phase-gate state machine as shell scripts the agent must *know to run* and discover through prose instructions in rules. That approach demonstrably fails even on OpenCode (the entire history of the `run-coverage-loop.sh` wrapper exists because the orchestrator *did not reliably call* `validate-phase-gate.sh` on its own — had to be wrapped in a counter). Making the agent discover validators via MCP tool catalog is strictly more reliable than instructing it in prose to run shell scripts. The build target is necessary but not sufficient.

## 8. Open questions for Bradford

1. **Where does the generation live?** Three options, all defensible:
   - (a) *In attest*: add `scripts/build-target-cursor.mjs`, keep output in `/dist/cursor/` or write to a sibling `../attest-cursor` repo on `--write` (same shape as `build-target-claude.mjs`). Mirrors the current pattern exactly, keeps one source of truth.
   - (b) *In a new `attest-cursor` repo* with its own `scripts/build-from-attest.mjs` pulling from a pinned attest commit. Decouples release cadence; cost is a second repo to maintain.
   - (c) *Direct install into consumer repos* (i.e., no intermediate repo, the build runs during `install.sh` and writes `.cursor/` straight into whichever project the user runs it in). Lightest-weight, but loses the parity-check CI gate because there is no second repo to diff against. Not recommended.

   My reading: (a) is cheapest and matches the attest-claude pattern perfectly. The attest-claude repo exists because Bradford committed to shipping to Claude Code too; the same reasoning says yes here.

2. **Does model-tier detection matter in Cursor?** My default answer is *no, drop it entirely* — all Cursor-selectable models are frontier. But there is a legitimate variant: Cursor's **Composer 2.5**, Claude **Haiku 5.5**, and GPT-5.4 **Nano/Mini** are the "cheap" tier. If Bradford still wants role routing (coder=cheap, reviewer=better, challenger=best), that generalizes to Cursor — `models.json`'s `roles` map becomes a hint custom subagents implement via their `model:` frontmatter field (`model: "claude-haiku-5-5"` on the coder subagent, `model: "claude-opus-5-5"` on the reviewer). Only the local 32k lane goes away; the plan-strong/execute-cheap split survives if desired.

3. **Should OpenCode and Cursor variants stay perfectly in sync?** This drives whether we care about a `build:cursor:check` CI gate on every PR. The Claude target has one and Bradford writes about the pain of forgetting the dual release (v1.23.0 referenced in `build-target-claude.mjs`). My recommendation is yes, same gate — adding a third parity test (opencode-cursor) is almost free once the shape is right.

4. **Is `attest-mcp` published as its own package, bundled in-repo, or shipped as a BDK subagent?** My recommendation is a standalone `attest-mcp` npm package (`npx --yes attest-mcp` in `.cursor/mcp.json`), which also makes it reusable from OpenCode and Claude Code. BDK is overkill here — this is a stdio tool server, not a hosted agent.

5. **How much of the "32k local model" discipline is still worth carrying on Cursor?** Specifically: `MICRO_LOOP.md`, `LOOP_PREVENTION.md`, `CHECKPOINT_STATE.md`, `BOUNDED_TASK_CONTRACT.md`, the task-ledger pattern, chunked synthesis. My view: keep the ones that are universally good hygiene regardless of model size (`BOUNDED_TASK_CONTRACT`, `CHECKPOINT_STATE`, `GATE_SCORING_PROTOCOL`, `CHALLENGER_PROTOCOL`, `FIX_VERIFY_LOOP`) and drop the ones that are patches for failure modes the frontier models don't exhibit (resume-anchor's per-request re-injection, the chunked synthesis extract-then-synthesize dance, the compact variants). The ones to keep translate cleanly into `.cursor/rules/` with glob and description.

6. **Does Bradford want the Cursor variant to carry the `plugins/` names (`attest`) or rebrand (`attest-cursor` for the generated repo, `attest-mcp` for the npm package)?** Mostly editorial, but affects every `description:` the user sees in Cursor Rules/Skills UI.

7. **What's the position on `agents/game/*` and the game cluster?** It's optional on OpenCode (`--no-game` flag, `--game-experts` to add). My default is include-by-default in Cursor since nobody edits a Cursor install, but easy to flip.

8. **Is `/autopilot` worth prioritizing or deferring?** The autopilot/conductor BDK port (Phase 2) is the biggest single piece of work. If Bradford's near-term Cursor users are mostly interactive, Phases 0+1 ship real value and Phase 2 can wait. If the pitch is "attest for Cursor cloud agents and Automations," Phase 2 moves to the front.
